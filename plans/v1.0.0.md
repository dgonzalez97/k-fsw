# K-FSW 1.0.0 — First Light

Proposed release and implementation plan. No functions changed. Builds, runtime
tests, and HIL were not run for this review.

## Requirement

Ship a stable, documented composition for Linux and NUCLEO-L496ZG. Make task
timing, failure reporting, and compatibility predictable before adding more
mission functions. Keep FRDM-K64F and Pico W at their documented bring-up scope.

I would use **First Light** for the first stable release. Start with
`v1.0.0-rc.1`; tag `v1.0.0` after the release checks below have evidence.

## Current behaviour

The ownership split and static allocation are good foundations. Keep them.
Most workers have fixed stacks, start explicitly, and sleep while idle.
Snapshots already use a shared temporary-file, sync, and rename implementation
(`kfsw-services/src/snapshot_file.c:30`). Extend its failure tests instead of
adding another persistence mechanism.

The remaining timing problems are in shared locks, blocking callbacks, and
completion rules. A fixed thread priority alone does not bound response time.
These are source findings; the interleavings below still need regression tests.

### Task setup

These are Kconfig defaults, not measured stack use or a resolved release
configuration. Smaller priority numbers run first; negative priorities are
cooperative. A blocked work handler holds up the other items on its queue.
See Zephyr's [scheduling](https://docs.zephyrproject.org/latest/kernel/services/scheduling/index.html)
and [workqueue](https://docs.zephyrproject.org/latest/kernel/services/threads/workqueue.html)
documentation. Defaults were checked in the local `v4.4.0` kernel Kconfig.

| Context | Priority | Stack bytes | Trigger / current limit |
| --- | --- | --- | --- |
| Main | 0 | 2048 | Startup, then application health reports |
| System workqueue | -1 | 1024 | Health, watchdog keepalive, temperature, button debounce, delayed reboot |
| CSP router | 0 | 2048 | Incoming packets; bound callbacks run here |
| PARAM list | 1 | 2048 | List requests; buffer waits and RDP sending |
| FTP acceptor / worker | 2 / 2 | 1536 / 3072 | One active transfer; default receive timeout 15000 ms |
| Command server | 2 | 3072 | Synchronous handlers; default receive timeout 10000 ms |
| HK server | 3 | 2048 | Requests for stored samples |
| Firmware upload | 3 | 2048 | Blocks; default receive timeout 8000 ms |
| HK collector | 4 | 2560 | 200 ms scan, serial local/remote collection |
| File procedures | 5 | 3072 | Start semaphore; one procedure; a wait permits 600 s by default |

Sources: `k-fsw/app/prj.conf:20`, `kfsw-comms/Kconfig:146`,
`kfsw-services/Kconfig:154`, and Zephyr `kernel/Kconfig:70` and `:603`.
Profile overrides matter: `nucleo-health.conf` selects a 500 ms health check
and a 4000 ms application deadline. Zephyr also supplies shell, idle, and any
selected driver threads; include them in the final configuration inventory.

## Root causes and proposed work

Each task is a separate change. Implement the named scope, add the specified
regression, then publish the dependency PR before updating `k-fsw/west.yml`.
Public signatures and wire formats stay unchanged unless a task explicitly
calls out a compatibility decision. All tasks below are proposed, not applied.

### D01 — Watchdog ownership and restored intervals

**Before 1.0.0 when health/watchdog is enabled. Depends on: none.**

- **Where:** `kfsw-platform/src/watchdog.c:68`,
  `watchdog_keepalive_handler()`; `:208`, `kfsw_platform_watchdog_release()`;
  `kfsw-services/src/health/health.c:270`, `kfsw_health_start()`; `:360`,
  `kfsw_health_check_interval_ms()`.
- **Finding:** release clears `keepalive_owned`, but the handler checks only
  `RUNNING`. Cancellation does not wait for an executing handler. A handler
  finishing across release can schedule another feed after health takes over
  on preemptible/SMP configurations. This interleaving was not observed on the
  default single-core cooperative workqueue.
  Also, parameters restore before watchdog initialisation; the interval check
  accepts any nonzero interval while the watchdog timeout is zero, and health
  start does not revalidate it against the armed watchdog.
- **Change:** check both ownership and state under the existing spinlock before
  feeding. Make release synchronise with an in-flight handler, outside the
  spinlock and only from a permitted thread context. Prevent further feeds or
  rescheduling after handover. Validate restored intervals against the configured
  watchdog timeout, then validate again before health takes ownership. Keep a
  safe compiled default when a restored value is rejected; report invalid
  compiled combinations during startup.
- **Acceptance:** force handover while the handler runs; subsequent platform
  feeds stay at zero. Restore a 5000 ms interval with an 8000 ms watchdog and
  confirm rejection before takeover. Exercise healthy, overdue, recovered,
  no-device, and repeated-start cases with a fake watchdog device. The current
  `k-fsw/tests/unit/platform_watchdog/` suite covers the no-device path.
- **Files:** the two source files, their public headers for context contracts,
  `k-fsw/tests/unit/platform_watchdog/`, `k-fsw/tests/unit/services_health/`.

### D02 — Remove the HK/PARAM lock cycle

**Before 1.0.0. Depends on: none.**

- **Where:** `kfsw-services/src/hk/hk.c:503`, `kfsw_hk_collect()`; `:405`,
  `kfsw_hk_collect_report()`; `src/hk-parameters/hk_table.c:29`, `sample_stats()`;
  `src/parameter/parameter_csp.c:389`, `param_server_callback()`.
- **Finding:** collection holds `hk_lock` while reading PARAM and remote nodes.
  PARAM sampling holds the parameter lock and requests HK statistics. This
  gives HK → PARAM and PARAM → HK acquisition orders. An interleaving can
  deadlock; remote waits also block access to samples already in the ring.
  The comment saying collection happens outside the lock is incorrect.
- **Change:** snapshot only the report definition under `hk_lock`, then release
  it before parameter reads or I/O. Serialise the existing scratch workspace
  with a separate collection mutex. Increment a generation counter on each
  clear/redefinition, preserving it across state resets; commit
  the sample under `hk_lock` only if the report still has that generation.
  Discard a sample from a cleared/redefined report with `-EAGAIN`. Accumulate
  statistics locally and update them with the ring. Snapshot pending store
  records and perform filesystem writes outside `hk_lock`, with bounded storage
  ownership and the same generation check. Do not copy the entire history ring.
- **Acceptance:** overlap collection with remote PARAM reads, report redefinition,
  clear, and a delayed filesystem write. Reads of an existing sample complete;
  no obsolete-layout sample enters the ring; simultaneous manual and scheduled
  collection cannot share unprotected scratch buffers.
- **Files:** `src/hk/hk.c`, `hk_internal.h`, `hk_remote.c`, `hk_store.c` in
  services; existing `k-fsw/tests/unit/services_hk*` suites.

### D03 — Flag failed remote samples

**Before 1.0.0. Depends on: none; coordinate with D02.**

- **Where:** `kfsw-services/src/hk/hk_remote.c:59`, `kfsw_hk_collect_remote()`.
- **Finding:** when a batch read fails after all names resolve, the failure
  counter advances but the function returns zero because `search.count` still
  equals `expected`. The sample's zero-filled values can be marked complete.
- **Change:** retain a failure result across every batch. Keep successful values
  and zero-fill failed ones, but return an error so the caller sets
  `KFSW_HK_FLAG_INCOMPLETE`. Preserve the existing wire layout.
- **Acceptance:** extend
  `k-fsw/tests/unit/services_hk_remote/src/main.c:193`,
  `test_read_failure_after_listing_still_counts_the_entries()`, to read the sample
  and assert the incomplete flag. Also cover one failed window among successes.
- **Files:** `src/hk/hk_remote.c` and that existing test file.

### D04 — Bound and finish remote PARAM transactions

**Before 1.0.0. Depends on: none; complete before D07.**

- **Where:** `kfsw-services/src/parameter/parameter_csp.c:416`, `serve_list()`;
  `:591`, `kfsw_param_remote_refresh()`; `:678`, `pull_remote_batch()`.
- **Finding:** a list iterator advances before buffer allocation; on exhaustion,
  `continue` skips that descriptor. A partially downloaded node is treated as
  cached once any descriptor exists. A pull sets `result = 0` after a valid
  fragment and can return success after a later timeout without `PARAM_FLAG_END`.
  Per-packet receive timeouts restart, so they are not total transaction bounds.
- **Change:** split into two PRs: list/cache completion, then value reads.
  Retry the same descriptor after a bounded buffer wait. Track cache completion
  per node and invalidate partial downloads on error. Use an absolute transaction
  deadline and a packet/descriptor bound. Require END and coverage of every
  requested value before returning read success; never supply stale cached
  values as a fresh result. Validate returned types and widths against the
  requested descriptors. Keep decoded results private until completion, without
  holding the parameter table lock across a CSP wait.
- **Compatibility decision:** verify whether the pinned RDP close exposes an
  unambiguous successful list end. If it does not, define a versioned completion
  marker before freezing the list protocol; silence alone is insufficient.
- **Acceptance:** buffer exhaustion followed by recovery; disconnect halfway
  through a list; missing END; missing requested values; duplicate fragments;
  packets trickling just inside the receive timeout. Each request has a bounded
  end and every received packet is released exactly once.
- **Files:** `src/parameter/parameter_csp.c`, private adapter state as needed,
  and a focused `k-fsw/tests/unit/services_param_csp/` suite (new). Keep the
  existing native PARAM integration scripts as end-to-end checks.

### D05 — Keep blocking PARAM work off the router

**Before 1.0.0. Depends on: D02 and D04.**

- **Where:** `kfsw-services/src/parameter/parameter_csp.c:389`,
  `param_server_callback()`; `k-fsw/app/src/parameters/telemetry_table.c:53`,
  `sample_storage()`; `kfsw-platform/src/storage.c:187`, `kfsw_storage_get_info()`.
- **Finding:** a value request samples every local definition in the router
  callback. Storage sampling calls `fs_statvfs()` under a mutex. Changed-value
  callbacks may also have synchronous side effects. Their latency becomes
  latency for routing unrelated packets.
- **Options:** make every callback operate on bounded cached state, or move
  value handling to a bounded worker. The latter contains existing blocking
  operations without changing every parameter owner.
- **Proposed change:** make the router callback enqueue the owned packet with
  `K_NO_WAIT`; a single static PARAM value worker runs the existing handler.
  Retain the separate list worker, whose paced/RDP transfer can wait. Define
  Kconfig stack, priority below the router, and queue depth with a reserved CSP
  buffer budget. On a full queue, free the packet and count the rejected request.
  Do not add heap allocation or a general dispatch framework.
- **Acceptance:** delay a filesystem operation while sending PARAM, ping, and
  transit traffic. The router continues; queue saturation is bounded; no packet
  leaks; write validation and protocol replies retain their existing semantics.
- **Files:** adapter source/private state, `kfsw-services/Kconfig`, PARAM adapter
  tests and a native routing/parameter integration case.

### D06 — Isolate sensor polling and report stale data

**Before 1.0.0 for the temperature profile. Depends on: none.**

- **Where:** `kfsw-modules/temperature-sensor-example/src/temperature_sensor_example.c:72`,
  `poll_work_handler()`; `:106`, `kfsw_temp_example_get()`;
  `src/temperature_sensor_example_sensor.c:26`, `kfsw_temp_example_sensor_read()`.
- **Finding:** synchronous sensor fetch runs on the system workqueue alongside
  health, watchdog, debounce, and reboot. The selected STM32 driver waits on a
  mutex and ADC completion (`zephyr/drivers/sensor/st/stm32_temp/stm32_temp.c:198`;
  `drivers/adc/adc_context.h:52`). A stalled fetch delays every queued item.
  Until a read returns failure, the cache can continue reporting an old value
  as valid.
- **Change:** submit the existing poll work to one module-owned static workqueue
  below the router. Give it a Kconfig stack/priority and a measured budget.
  Mark readings invalid once their monotonic age exceeds a documented maximum;
  keep PARAM reads as cache copies. An unavailable sensor should not hold up
  unrelated health checks. Decide separately whether this module is critical
  enough to request a watchdog reset.
- **Acceptance:** stall the fetch longer than a health period; health and reboot
  work still execute, the reading becomes stale, and recovery refreshes it.
  Measure the additional stack/RAM cost on NUCLEO.
- **Files:** the two module source files, its Kconfig/header, and
  `kfsw-modules/tests/temperature_sensor_example/`.

### D07 — Give periodic collection an explicit timing policy

**Before claiming bounded periodic timing. Depends on: D02, D04, D05, D06.**

- **Where:** `kfsw-services/src/hk/hk_thread.c:29`, `hk_collector()`;
  `src/hk/hk.c:673`, `kfsw_hk_set_period()`; `src/hk/hk_remote.c:59`,
  `kfsw_hk_collect_remote()`.
- **Finding:** one `now` value covers the entire scan. Each due time becomes
  `now + period`, followed by collection and another 200 ms sleep. Slow remote
  work delays later reports and can leave a deadline already expired when the
  next pass begins. There is no declared missed-period policy or total budget
  for a remote report.
- **Change:** retain the existing collector thread. Use absolute monotonic due
  times and advance each report to the first future slot after completion;
  skip missed slots and count them. Refresh time before each due decision.
  Sleep until the next due report, with a semaphore wake for configuration
  changes. Bound total remote work per report and mark budget expiry incomplete.
  Keep wall-clock validity as the timestamp policy; wall-clock adjustments must
  not move the monotonic schedule.
- **Acceptance:** delayed work longer than one and several periods, two reports
  with different periods, stop/resume, period changes, clock loss/recovery,
  and a silent remote node. Assert due times and missed counts with controlled
  time; keep one real-thread integration case. No catch-up burst.
- **Files:** the three service files, `hk_internal.h`, HK stats/header if a
  missed counter is exposed, and existing HK collector/remote tests.

### D08 — Make startup results match the running services

**Before 1.0.0. Depends on: D01.**

- **Where:** `k-fsw/app/src/main.c:82`, `main()`;
  `kfsw-services/src/fwu/fwu_lite_csp.c:167`, `kfsw_fwu_lite_server_start()`;
  `:123`, `server_entry()`; `src/boot.c:44`, `kfsw_boot_service_start()`.
- **Finding:** the HK server starts at main line 329 before HK initialises at
  line 342. Firmware upload reports success before its thread binds/listens;
  a later bind failure exits the thread while `server_running` stays true.
  `@READY` is unconditional, and HK start's return value is discarded.
- **Change:** initialise state before making its interface reachable, and check
  each start result. If restoring remote HK definitions requires the router,
  separate state initialisation from restore/activation and gate inbound HK
  operations until restore finishes. Bind/listen synchronously in firmware
  server start, as the HK and command servers already do; close on failure and
  permit a retry. Keep `@READY` as a startup-complete marker for existing tools,
  and add a separate service-status/degraded result. Define which failures
  permit a diagnostic shell and which prevent normal operation.
- **Acceptance:** force port collisions, missing storage, corrupt definitions,
  and failed service initialisation. No server reports running after failure;
  early requests cannot use uninitialised state; minimal compositions still
  start. Validate the proposed failure policy before changing unattended resets.
- **Files:** the named source files, public startup/status headers as required,
  firmware server tests and native boot/integration scripts.

### D09 — Bound procedure cancellation and numeric input

**Before supporting unattended procedures in 1.0.0. Depends on: none.**

- **Where:** `kfsw-services/src/fbo/fbo.c:168`, `run_line()`; `:234`,
  `run_procedure()`; `:390`, `kfsw_fbo_run()`; `:444`, `kfsw_fbo_stop()`;
  `src/command/command.c:172`, `kfsw_command_parse_arg()`.
- **Finding:** stop sets a flag but cannot interrupt `k_sleep()` in a wait
  line; the default maximum wait is ten minutes. Stopping while idle leaves
  a flag that can stop the next procedure. File read errors are treated as EOF.
  `strtoul`/`strtol` conversions do not check overflow, and event IDs narrow to
  16 bits without range checks; behaviour differs with host integer width.
- **Change:** two small PRs: cancellation/read outcomes, then numeric parsing.
  Use an interruptible semaphore wait and clear cancellation at a defined run
  boundary. An idle stop must not affect the next run. Preserve filesystem
  errors in status. Check unsigned signs, conversion errors, and destination
  width before casts. Bound bytes scanned as well as executable lines.
- **Acceptance:** stop during the longest wait, stop while idle then run, read
  failure, oversized/comment-only input, `-1`, overflow beyond 32 bits, and an
  event ID above 65535. Test target-width parsing, not only a 64-bit host.
  Set and verify a stop-latency requirement; do not promise cancellation of an
  arbitrary synchronous command handler before that handler returns.
- **Files:** the two sources, FBO status/header and Kconfig if needed,
  `k-fsw/tests/fbo-smoke.sh`, `tests/unit/services_command/`, and focused FBO
  unit cases (new).

### D10 — Define safe runtime route changes

**Before 1.0.0. Depends on: none.**

- **Where:** `kfsw-comms/src/csp.c:84`, `load_route_table()`; `:104`,
  `kfsw_csp_route_table_apply()`; `k-fsw/app/src/parameters/csp_table.c:75`,
  `apply_route_table()`.
- **Finding:** replacement clears and reloads libcsp's shared table. Its CIDR
  implementation returns pointers into that table, and transmit paths use
  them outside any K-FSW lock. Concurrent shell/PARAM updates and traffic can
  observe a cleared or partial route. A mutex around writers alone is insufficient.
- **Options:** coordinate every route reader and writer through a supported
  libcsp mechanism, or limit replacement to startup.
- **Proposed 1.0.0 scope:** reject runtime replacement after the router starts,
  expose the setting as read-only in that profile, and retain compiled startup
  routing. If live replacement is a release requirement, resolve reader lifetime
  and acknowledgement over the old route first; do not suspend only the router,
  since other threads also transmit. No local vendor-source patch.
- **Acceptance:** attempt replacement from shell and remote PARAM during
  traffic; rejection leaves the effective table unchanged. Startup routes,
  invalid routes, VIA, loopback, and two-link transit retain their tests.
- **Files:** comms source/header, the composition table, routing/parameter tests,
  and route documentation after the behaviour is agreed.

### D11 — Report firmware cleanup failures

**Before 1.0.0 with firmware update enabled. Depends on: none.**

- **Where:** `kfsw-services/src/fwu/fwu.c:360`, `kfsw_fwu_abort()`.
- **Finding:** abort ignores the slot erase result, clears counters, sets IDLE,
  and returns success. An erase failure can leave data or upgrade metadata in
  a slot that the caller was told had been cleared.
- **Change:** return the erase error and retain an explicit failed state when
  cleanup fails. Audit callers so neither the protocol nor shell prints a
  successful abort. Keep bootloader validation responsible for signatures.
- **Acceptance:** inject erase failure, check return/status and reply, retry
  cleanup, and restart an upload. On hardware, verify the old image remains
  recoverable after interrupted upload and failed cleanup.
- **Files:** `src/fwu/fwu.c`, abort callers only where they discard the result,
  and existing `k-fsw/tests/unit/services_fwu*` cases.

### D12 — Expose failed HK persistence

**Before promising persistent HK configuration in 1.0.0. Depends on: D02.**

- **Where:** `kfsw-services/src/hk/hk.c:202`, `kfsw_hk_define()`; `:296`,
  `kfsw_hk_clear()`; `:562`, `kfsw_hk_set_store()`; `:673`,
  `kfsw_hk_set_period()`; `:732`, `kfsw_hk_init()`.
- **Finding:** these paths discard save/load results. A configuration change
  can succeed in RAM, fail to reach storage, and disappear on reset without
  the caller learning it was not saved.
- **Change:** keep the runtime change but return/report persistence failure
  separately and expose a dirty/error state. On boot, distinguish an absent
  snapshot from a rejected one. Apply the same rule to beacon persistence.
  Avoid rolling back a live change implicitly after reporting success.
- **Acceptance:** no space, write/sync/rename failure, corrupt snapshot, retry,
  and reset. The operator can distinguish active state from saved state.
- **Files:** HK source/persistence helpers and public status contract,
  shell/command callers, existing HK persistence/store tests.

## Implementation order and file scope

1. D01, D02, D03, D04, D08: health, locking, data integrity, and startup.
2. D05 and D06: isolate blocking work; then D07: measure and bound scheduling.
3. D09–D12: finish the enabled procedure, routing, update, and persistence contracts.
4. D13: freeze inputs and prepare the release candidate.

Each task's **Files** entry is its expected edit boundary. Several tasks touch
HK or PARAM: land D02 before changing collection scheduling or persistence;
land D04 before changing the adapter's execution context. Rebase on the merged
dependency and refresh line references. Split tests/integration and the manifest
pin into the owning composition PR. Do not rename unrelated APIs, move entire
services, or introduce a scheduling framework during these fixes.

## Timing acceptance

For every enabled thread and workqueue, record owner, trigger, priority, stack,
maximum execution time, blocking time, deadline, and behaviour on overload.
Record IRQ load and the resolved tick/time-slice settings as well. Treat the
priority table above as an inventory, not a schedulability proof.

Use maximum observed wake-up lateness, execution duration, lock wait, stack
usage, missed periods, and minimum free CSP buffers. Measure concurrent
collection, PARAM reads/writes, file transfer, and flash erase with logging at
the supported levels. Add dead peers and dropped packets. Keep the results
tied to the image, configuration, workload, and test duration.

For health, the largest permitted check gap plus feed duration must fit inside
the watchdog timeout with an explicit margin. For HK, define the maximum
lateness and missed-slot rule per report. For procedures, distinguish stop
request acceptance from the time the current operation actually ends.
Choose numeric limits for the reference workload before acceptance; this review
does not invent timing guarantees from source alone.

Only the application loop currently registers with health in the composition
(`k-fsw/app/src/main.c:381`). Define meaningful progress/deadline checks for
critical enabled workers, including normal idle periods. Do not add heartbeats
that keep reporting while the work they are supposed to supervise is stuck.

## Decisions before the first tag

- **Supported scope:** choose the exact Linux/NUCLEO profiles. Optional features
  with open correctness tasks stay outside the supported release configuration
  until fixed and checked. More boards and additional mission modules can follow.
- **Compatibility:** freeze public headers, Kconfig names, PARAM IDs/types/modes,
  command IDs/arguments, CSP ports, wire formats, snapshot versions, and ground
  decoder expectations. Define the deprecation/migration rule. Version 1.0.0
  establishes a public API under [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
- **Publication:** the reviewed platform, services, and comms commits were each
  one commit ahead of their main branches; modules matched main. Merge the
  chosen dependency changes and pin the final commits before freezing a candidate.
- **Licence and notices:** the reviewed owned repositories have no root licence
  file. The maintainer must choose the project licence and confirm dependency
  notices before distributing a stable release. No licence is selected here.
- **Operational boundary:** document the trusted-link assumption. CRC and a
  reboot PIN do not provide command authentication. If an untrusted command
  link is in release scope, define authentication/replay protection before
  calling that configuration supported.
- **Release contents:** short changelog, supported profiles, installation and
  recovery steps, known limits, source/archive hashes, manifest, and acceptance
  record. Keep stable release documentation tied to the tag.

## Risks and open questions

The main decisions are the supported profiles, whether live route replacement
is required, command-link trust, timing limits, and the licence. They affect
release scope; they do not prevent preparing the documentation PRs.

The worker proposals add bounded RAM/stack cost. Measure it before selecting
defaults. Mutex or priority changes alone cannot make a blocking driver meet a
deadline. An isolated sensor can still stall its own queue, so stale-data and
recovery behaviour remain necessary.

This review covers the composition, task setup, the cited service paths,
representative tests, and release tooling. It is not exhaustive runtime,
electrical, or flight-qualification evidence. Revalidate findings against
concurrent work before turning a task into a code change.
